## What the suite is

The checklist has ~110 individual stories. Turning each into a bespoke test would
duplicate coverage that already exists (and rot), so FG5 is built as **traceability
plus gaps**:

1. **`core/test/stories/registry.ts`** — every story from the checklist with a
   stable id (`BOOT-001`, `MEM-010`, …), a title, and exactly one status:
   - `automated` — cites a real test (file + exact title);
   - `live` — only provable with a real model/channel/configuration, with the
     configuration named;
   - `deferred` — deliberately out of 1.0, with the reason.
2. **`core/test/stories/registry.e2e-spec.ts`** — enforces the rules on every
   run:
   - ids unique and well formed;
   - no story without a decision, and `live`/`deferred` require a reason;
   - **every `automated` proof's file exists and still contains that test** — a
     renamed or deleted test fails the suite instead of silently dropping
     coverage;
   - the committed matrix matches the registry byte-for-byte.
3. **`.reference/plans/release-1.0-story-matrix.md`** — generated by
   `npm run stories:render`; the document cannot drift from the registry.
4. **New story tests** for the journeys that had no coverage at all.

## Honest remainder

- **Live stories are not executed here.** 37 entries need a real model
  (CODE-*), a real Discord/email channel (DISC-*, CHAT-009/010), a live MCP server
  (MCP-004..006), or a specific boot configuration (BOOT-001's 18-cell matrix,
  currently 3 cells). The registry names what each needs; a release run has to
  tick them.
- **Deferred stories are product decisions, not test gaps.** Document reading
  (no extraction), audio attachments (not in the allowlist), KB save from chat,
  audit email, and outbound attachments are called out in the matrix.
- **UI consistency (UX-004/005) is judged, not asserted.** GH21's evidence
  (computed styles + AXE) is the mechanism; there is no cross-tab visual
  regression test.
- The matrix is generated; edit the registry, never the markdown.
